# Responsibilities

`WebMaster` is the mitmweb master. It holds the same `Options` as the other
front ends and adds the web UI. It listens for option changes and broadcasts
them to browsers. `webaddons.py` declares the `web_*` options and handles
authentication. `app.py` is the Tornado application that serves the UI and
exposes the options over REST: `GET /options` dumps everything with
`optmanager.dump_dicts`, and `PUT /options` calls `master.options.update(**json)`
and returns 400 with the error message if that fails.

# Dependencies

- Option declarations for `web_*` come from [OptManager](optmanager.md) through `loader.add_option`, the same mechanism the proxy addons use.
- Its startup flags are produced by [CLI options](cli-options.md) (`mitmweb` adds `--web-open-browser`, `--web-port`, `--web-host`).
- The browser side is generated by [Web code generators](web-gen.md): `_options_gen.ts` is produced from `WebMaster(Options()).options`, so the option types used by the UI come from the same declarations.
- `WebMaster` subscribes to the proxy server's `servers` signal and broadcasts `state/update`, which is how server mode changes reach the UI.

# Gotchas

- **Auth cookie is per port.** The cookie name is `mitmproxy-auth-<web_port>`, so two mitmweb instances on different ports do not overwrite each other. The naming was originally shared, which let concurrent instances clobber each other's cookie (`790f000e`, `#7690`), and a later fix made it follow the `web_port` value actually in use (`f6d27fad`, `#7827`).
- **Password hashing rules.** A `web_password` starting with `$` must be a valid argon2 hash, or the option errors. A plain-text password logs a warning recommending a hash. If no password is set, a random token from `secrets.token_hex(16)` is used.
- **Port collision advice.** When the web listener fails, the message suggests `--set web_port=<port + 2>`, not `+1`. The change to `+2` was made to avoid clashes with mitmweb (`934b92a0`, `#6221`).
- **Option updates are live and global.** The broadcast uses the same `changed` signal as the CLI, so a browser change takes effect in the running proxy immediately, with the same rollback behaviour as [OptManager](optmanager.md).
